Why this paper matters

Two grad students vs. the GPU industry

By 2022, attention was the bottleneck of every transformer. The implementations that mattered came from teams with deep GPU expertise:

  • NVIDIA — cuDNN, Apex, FasterTransformer. Hand-tuned by the people who designed the hardware.
  • Hugging Face — the reference implementation every researcher imported.

Then a paper showed up from two PhD students at Stanford with a kernel they wrote themselves. It was faster. By a lot. And it used less memory.

One CUDA kernel. No new approximation. Just a better understanding of the memory hierarchy.

Why this problem exists

We want to model longer sequences

  • NLP — large context to understand books, plays, long documents.
  • Vision — higher resolution → more tokens → better, more robust features.
  • Other data — time series, audio, video. Sequences of millions of steps.
The catch: attention is O(N²) in both time and memory — double the sequence length, quadruple the cost.

Why long sequences hurt

The N×N attention score matrix is the bottleneck. At sequence length N, it holds N² entries that must be materialized, written, and read back from HBM.

What people tried before FlashAttention

Background: approximate attention

The pre-FlashAttention playbook: trade quality for speed — kill attention's O(N²) cost by either skipping token pairs (sparse) or factorizing the score matrix (low-rank).

Sparse

attend to only a subset of token pairs

  • Sparse Transformer Child et al. '19
  • Reformer · LSH Kitaev et al. '20
  • Routing Transformer Roy et al. '20

Low-rank

approximate softmax(QKᵀ) by rank-r factors

  • Linformer Wang et al. '20
  • Linear Transformer Katharopoulos et al. '20
  • Performer · FAVOR+ Choromanski et al. '20

The whole zoo — sparse and low-rank — shares one weakness: they all chase FLOP reduction and trade away exactness. None delivered a real wall-clock speedup at typical sequence lengths, because the true bottleneck wasn't compute. That's the gap the next slide sets up.

The motivating observation

So why didn't any of these win?

  • None of them showed a wall-clock speedup over vanilla attention at typical sequence lengths.
  • They all trade quality for FLOPs — and on hard benchmarks the quality drop is real.
They optimized the wrong thing — FLOPs, when the bottleneck was IO.

Modern GPUs are compute-rich, memory-poor. H100 does ~989 TFLOPS of FP16 tensor, but HBM bandwidth is ~3.35 TB/s. Most attention kernels spend their time waiting on memory, not computing.

Quick quiz: what really separates an RTX 3090, a 3080 Ti, and a 3080?

They're the exact same chip — the GA102 die. Same silicon, same memory layout. The only difference is how many SMs are switched on.

Why? Manufacturing a 28-billion-transistor die isn't perfect — most come out with a few defective SMs. Instead of scrapping the whole wafer, NVIDIA fuses off the broken units and sells the die a tier down. A chip with 2 bad SMs becomes a 3090; one with 16 bad SMs becomes a 3080. This is "binning" — defect harvesting. The green squares above are working SMs; the dark ones are disabled.

Tab 1: click through the four pieces in order — HBM → L2 → GPC → SM — that ordering builds the mental model the rest of the talk leans on. Tab 2 is a palate-cleanser fun fact: the whole 30-series GA102 stack is one die binned by how many SMs survived fab. Ties back to "an SM is the unit of compute" — you literally pay per working SM.

GPU 101 · why GPUs are the right hammer

A GPU craves parallel work — attention has it in spades

SIMT — one instruction, a whole warp of threads

A GPU broadcasts a single instruction across a 32-thread warp and keeps thousands of warps in flight at once. It's a pure throughput machine: give it enough independent work and every lane stays busy. So the only question is — does attention actually have that much parallelism?

Yes — attention is embarrassingly parallel along three axes

Attention heads

tiles processed independently

N / Bq = 32 tiles

B × H × N/Bq ≈ 32 768 independent jobs per step → FA1 launches one CUDA block per (batch, head, query-tile). A 132-SM GPU eats it.

Frame it as a question-and-answer: a GPU is a throughput machine that just needs independent work to stay full — does attention have it? Yes, on three axes that never talk to each other. Click an axis card. Punchline: multiply them → ~32k independent jobs → one CUDA block each, and a 132-SM GPU eats it.

Where attention lives: layers & heads

A model is L layers deep; each layer runs H heads in parallel, then concatenates and projects them into the input of the next layer. So the Q·Kᵀ→softmax→V we just walked through happens H × L times per forward pass (GPT-3: 96 × 96 ≈ 9,216).

The roadmap for the next few slides

The authors' hypothesis

An IO-aware attention algorithm can close the gap.
  • Carefully account for reads/writes between fast memory (SRAM, registers) and slow memory (HBM).
  • Standard DL frameworks (PyTorch, TF) don't expose fine-grained memory control — so we have to drop down to CUDA.

Two engineering goals we'll meet in this section

  1. Compute the softmax reduction without materializing the full input.  →  we'll derive this via online softmax + block tiling (next 4 slides).
  2. Don't store the giant attention matrix for the backward pass.  →  we'll handle this with recomputation.

The destination: an attention algorithm that computes exact attention while accessing memory far less. Faster wall-clock and less memory than the previous approximation work — with zero quality trade-off.

Lay this out as the contract before the math starts. Everything in the next 8 slides earns one of these two goals.

Step 1 — the softmax row

Softmax looks trivial to parallelize

pointwise nonlinear op
σ(z)i  =  ezi Σj=1K ezj
reduction over the same values

The numerator is embarrassingly parallel — every element independent.
The denominator is a sum reduction — also a standard primitive.

So what's the problem?

For attention, z is a row of QKᵀ, length N. To compute the softmax of one row you need to:

  1. Read all N values to find the sum (pass 1)
  2. Read them all again to divide by the sum (pass 2)
  3. And — there's also overflow. ez blows past FP16's max (~65 504) for z > 11. So we need a third pass first, just to find the row max and subtract it.

Three N-length passes through HBM. And it gets worse…

▸ drag past z = 11 and watch one cell explode — that's why the third pass exists

Step 3 — the intuition

Online softmax: fuse three passes into one

The trick: maintain the running max and the running normalizer in lockstep. Whenever a new max arrives, rescale the partial sum by a single scalar — α = exp(m_prev − m_new). Math identical, just one walk through the data.

Step 3 — derivation

Why online softmax works — step by step

Safe softmax · three sequential passes

$m_0 = -\infty$
for $1 \le i \le N$:
$m_i = \max(m_{i-1},\, x_i)$ // pass 1 — row max
$d_0 = 0$
for $1 \le i \le N$:
$d_i = d_{i-1} + e^{\,x_i - \,}$$m_N$ // pass 2 — needs the final $m_N$
for $1 \le i \le N$:
$a_i = e^{\,x_i - m_N} / d_N$ // pass 3 — normalise
The red $m_N$ is the obstacle. Pass 2 can't start until pass 1 has finished the entire row. Three sequential passes over x.

Idea: replace the final max with the running max

old $\;\;d_i \;=\; \displaystyle\sum_{j=1}^{i} e^{\,x_j -\,}$$m_N$
uses the final max — must wait for pass 1
new $\;d'_i \;=\; \displaystyle\sum_{j=1}^{i} e^{\,x_j -\,}$$m_i$
uses the running max — computable online
At the end of the row: $d'_N = d_N$.  (because $m_N$ is the running max and the final max — they agree.)
So if we can compute $d'_i$ incrementally, we get $d_N$ for free at the end. We just need a recurrence: $d'_i$ in terms of $d'_{i-1}$.

Build $d'_i$ from $d'_{i-1}$ — 5 algebraic moves

$d'_i \;=\; \displaystyle\sum_{j=1}^{i} e^{\,x_j - m_i}$
definition
$\phantom{d'_i}\;=\; \displaystyle\sum_{j=1}^{i-1} e^{\,x_j - m_i} \;+\; e^{\,x_i - m_i}$
split off the last term
$\phantom{d'_i}\;=\; \displaystyle\sum_{j=1}^{i-1} e^{\,x_j - m_i} \cdot \underbrace{e^{\,m_{i-1}} \cdot e^{\,-m_{i-1}}}_{=\,1} \;+\; e^{\,x_i - m_i}$
multiply by $1 = e^{m_{i-1}}\!\cdot e^{-m_{i-1}}$
$\phantom{d'_i}\;=\; \displaystyle\sum_{j=1}^{i-1} \bigl(e^{\,x_j - m_{i-1}} \cdot e^{\,m_{i-1} - m_i}\bigr) \;+\; e^{\,x_i - m_i}$
regroup exponents into $(x_j - m_{i-1}) + (m_{i-1} - m_i)$
$\phantom{d'_i}\;=\; \Bigl(\displaystyle\sum_{j=1}^{i-1} e^{\,x_j - m_{i-1}}\Bigr) \cdot e^{\,m_{i-1} - m_i} \;+\; e^{\,x_i - m_i}$
pull the constant out of the sum
$\phantom{d'_i}\;=\;$$d'_{i-1} \cdot e^{\,m_{i-1} - m_i} \;+\; e^{\,x_i - m_i}$
the highlighted sum is $d'_{i-1}$ ✓
The whole trick is the "multiply by 1" move: insert $e^{m_{i-1}} \cdot e^{-m_{i-1}} = 1$, then regroup so the $m_i$ in the exponent becomes $m_{i-1}$. That re-uses the already-computed $d'_{i-1}$. The scalar $e^{m_{i-1} - m_i} \le 1$ is the rescale factor $\alpha$ — it deflates the old partial sum so the new max can take over.

for $1 \le i \le N$:
$m_i = \max(m_{i-1}, x_i)$
$d_0 = 0$

Online softmax · 2 passes

$m_0 = -\infty,\; d'_0 = 0$
for $1 \le i \le N$:
$m_i = \max(m_{i-1}, x_i)$
$d'_i = d'_{i-1}\, e^{m_{i-1} - m_i} + e^{x_i - m_i}$
for $1 \le i \le N$:
$a_i = e^{x_i - m_N} / d'_N$
// $m$ and $d'$ fuse into one loop · $d'_N = d_N$
$m$ and $d'$ now walk together in one pass. Reads of $x$: 3N → 2N. The normalisation loop still needs $m_N$ and $d'_N$ — but those are final scalars, so they're ready when this loop ends.

FlashAttention forward · fold $S = QK^\top$ and $O = AV$ into the same loop

$m_0 = -\infty,\;\; d'_0 = 0,\;\; o_0 = \mathbf{0}$
for $1 \le i \le N$:
$x_i = q \cdot k_i^{\top}$ // one row of $S$, computed on the fly
$m_i = \max(m_{i-1},\, x_i)$
$d'_i = d'_{i-1}\, e^{m_{i-1} - m_i} \;+\; e^{x_i - m_i}$
$o_i = o_{i-1} \cdot \dfrac{d'_{i-1}}{d'_i}\, e^{m_{i-1} - m_i} \;+\; \dfrac{e^{x_i - m_i}}{d'_i}\, v_i$ // same trick, applied to $O$
return $o_N$
One pass over K and V. The full N×N $S$ and $A$ matrices never get written. The last line is the same recurrence as $d'_i$ — just now the "value being scaled" is the running output vector $o$ instead of the normaliser.

Walk slowly through step 2 — the third line is the whole derivation. Frame steps 3 and 4 as "once you have the rescale lemma, attention is just two of these recurrences in one loop." Step 4's $o_i$ recurrence is literally what FA1 implements inside the kernel.

The backward pass

Recomputation in the backward

Forward saves only:

  • O  (N×d, the output — you'd save this anyway)
  • m, l  (N, the softmax statistics per row)

That's it. No S, no P. We've avoided two N×N matrices.

In backward

Re-tile through Q, K, V. For each (i, j) block, recompute Sᵢⱼ and Pᵢⱼ in SRAM using the saved (mᵢ, lᵢ) — no numerical issues, no extra HBM reads. Then compute the gradients dQ, dK, dV using the standard chain rule.

The sequel · 2023

FlashAttention-2 — same math, better hardware fit

FA1 was IO-optimal but still left the GPU ~25–40% utilized — too many non-matmul ops and idle SMs. FA2 keeps the exact-attention guarantee and just reorganizes the work.

1 · Parallelize over sequence length

FA1 only split work across batch × heads. FA2 also tiles along the query dimension, so even at small batch / few heads every SM has work.

2 · Better work partitioning

Swap the loop order so each warp owns a fixed slice of the output and the K/V tiles stream past it — fewer shared-memory round-trips and warp syncs.

3 · Fewer non-matmul FLOPs

Rework the online-softmax rescaling so the expensive non-matmul ops shrink. Tensor cores stay fed instead of stalling on element-wise math.

Result: ~2× faster than FA1 · 4–8× faster than naïve attention · up to ~230 TFLOPS on A100 (≈72% of peak FP16).

The key insight: FA1 solved the memory problem; FA2 solved the occupancy problem. Same exact output, but the kernel now actually keeps the tensor cores busy.

Hopper era · 2024

FlashAttention-3 — built for the H100

FA2 was tuned for Ampere. The H100 (Hopper) added hardware FA2 couldn't reach — so FA3 rewrote the kernel around three new primitives:

  • Async WGMMA — warp-group matrix multiply that issues without blocking the warp.
  • TMA — Tensor Memory Accelerator does async global→shared copies, freeing threads from address math.
  • Native FP8 tensor cores — half the bytes, double the throughput.

Result: ~1.5–2× faster than FA2 · up to 75% H100 utilization · ~740 TFLOPS FP16, ~1.2 PFLOPS FP8.

Warp specialization — overlap load & compute

Producer warps issue TMA loads; consumer warps run WGMMA + softmax. While one tile computes, the next is already streaming in.

The theme of the whole series: each version chases the next bottleneck. FA1 = memory, FA2 = occupancy, FA3 = Hopper's async engines + FP8.

Blackwell era · 2026

FlashAttention-4 — chasing the Blackwell B200

Published March 2026. On Blackwell the bottleneck moved again — the special-function unit (SFU) that computes exp() for softmax couldn't keep up with the tensor cores. FA4's fixes:

exp() on the FMA units

Approximate the exponential with a polynomial on the general-purpose FMA units instead of routing every value through the slow SFU — Blackwell has FMA throughput to spare.

Redesigned async pipeline

Orchestration warps drive TMA loads + matmul scheduling while compute warps run softmax — deeper warp specialization than FA3.

Conditional rescaling + CuTe-DSL

Only rescale when numerical stability needs it (~10× fewer rescales). Written in the Python-embedded CuTe-DSL — compiles in seconds.
